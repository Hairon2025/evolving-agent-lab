# 代码规范

本规范约束**新增和修改的代码**。当前仓库仍有演示代码与预留空文件；它们不是目标实现，也不要求为满足规范一次性重写。每次改动应解决一个明确问题，并保持可运行、可验证。

## 1. 模块与依赖

- 优先按业务或运行职责放置代码。Agent 构建放在 `agent_runtime/agents/`，工具适配放在 `agent_runtime/tools/`，预订模型放在 `models/booking/`。
- 入口代码负责输入输出和依赖组装；Tool 负责调用业务操作；预订模块负责业务规则；持久化适配器负责数据库访问。
- `models/booking/` 不导入 `agents` 或数据库连接。Agent Context 不作为订单或座位库存的事实来源。
- 允许 `agent_runtime` 依赖预订业务接口，不允许预订业务模块反向依赖 `agent_runtime`。
- 跨模块 `infrastructure/` 放数据库连接、事务等共用设施；预订专属的 SQL 查询实现应留在预订模块的适配代码中。没有实现前不创建空的接口或抽象类。
- 避免循环导入。互相 Handoff 的 Agent 统一在 Factory 中组装。

## 2. Python 风格

- 文件、函数和变量使用 `snake_case`；类使用 `PascalCase`；常量使用 `UPPER_SNAKE_CASE`。
- 导入顺序为标准库、第三方库、项目内模块，组之间空一行；项目内使用 `evolving_agent...` 绝对导入。
- 对公开函数、Tool 和核心业务方法标注参数与返回类型。跨层传递的数据结构应有明确类型，不用无说明的任意字典。
- 函数保持单一职责。条件分支变复杂时先抽出业务函数；不要按固定行数机械拆文件。
- 注释解释业务约束或不明显的原因，不重复代码表面行为。删除失效注释和长期保留的注释掉的旧实现。
- 新增代码按项目已采用的 Python 版本编写；引入格式化或静态检查工具时，在 `pyproject.toml` 固定配置，不依赖个人编辑器设置。

## 3. Agent、Handoff 与 Tool

- Agent 指令明确职责、可用工具、成功条件和无法处理时的行为；更改指令时记录所验证的场景。
- Handoff 只负责转交控制权和记录意图，不生成航班号、订单号等业务事实。
- Tool 的参数描述清楚输入格式、业务副作用、错误返回；有副作用的 Tool 只在业务层确认成功后返回成功。
- Tool 不直接修改 Context 来冒充业务持久化。可在业务操作成功后把已验证结果同步进 Context。
- FAQ 或政策数据没有覆盖问题时，明确返回“未覆盖”；Agent 不得自行编造政策、价格或承诺。
- 为一次 Agent 运行设置合理的最大轮数；保存必要的路由、工具调用和错误信息，便于之后评估。记录日志时不输出 API Key 或不必要的客户信息。

## 4. 业务模型与持久化

- `Booking` 表达预订业务数据；会话 Context 表达当前对话状态；未来的 ORM 类表达数据库表结构。三者不要互相替代。
- 确认号不存在、目标座位不可用、座位格式错误等属于可预期业务失败，用明确的错误类型或结果表示，不用 `assert`。
- 更新座位时必须先校验预订与库存，再执行变更；有数据库后应在同一事务中完成，防止重复占座或只更新一半。
- 数据库凭证与模型密钥从环境变量或密钥管理服务读取。仓库只提交不含真实值的示例配置。
- Repository 的接口保持业务语义，如 `get_booking`、`list_available_seats`、`change_seat`；不要把 SQLAlchemy 对象直接传到 Agent Tool。

## 5. 错误处理与配置

- 配置缺失应在启动时给出清楚的错误；避免模块导入时执行不必要的外部调用或隐式副作用。配置来源与默认值要明确。
- 捕获异常时区分业务错误、模型/网络错误和程序错误。不要用裸 `except` 后返回“成功”。
- 对外错误信息稳定、简短；内部日志保留足够上下文用于排查，但不泄露密钥或敏感数据。
- 每个会话独立创建 Context 和运行状态；不要用模块级可变对象共享客户会话数据。

## 6. 测试与改动完成标准

- 业务规则先写不依赖模型服务的单元测试，至少覆盖成功、无效输入、资源不可用和失败后状态不变。
- Agent 集成测试检查路由、必需工具调用、错误后的最终回复；尽量使用固定输入或可替换的模型，避免把真实模型调用当作唯一测试。
- 修复缺陷时增加能复现缺陷的测试；纯文件搬迁可以用导入检查和现有测试验证，不必写与实现同形的测试。
- 提交前运行与改动相关的检查；若未运行真实模型或数据库集成测试，在改动说明中明确写出。
- 一次提交聚焦一个可理解的变更。修改模块边界或运行方式时同步更新本结构文档和 README。
